## D-01 · TypeScript monorepo — Proposed
- **Decision:** TypeScript (strict) in every app and package. pnpm workspaces + Turborepo. Biome for lint and format.
- **Why:** one language end to end. Zod schemas and types are shared by `api`, `pos-web` and `liff-web`, so a change to an order field breaks the build instead of production. Turborepo caches build/test per package.
- **Alternatives:** Nx (heavier); separate repos (types drift); ESLint + Prettier (two tools instead of one).
- **Revisit if:** a lint rule we need exists only in ESLint.

## D-02 · Backend runtime — Proposed
- **Decision:** Node.js 24 LTS (move to 26 LTS once it enters LTS in Oct 2026), Fastify 5, `fastify-type-provider-zod`, Pino logging, `@fastify/websocket`, `@fastify/rate-limit`, official `@line/bot-sdk`.
- **Why:** the owner already plans Fastify for ntfy. It is fast and schema-first. The same container runs on the Oracle VM, the future Mini PC, or any Docker host, so we are not locked to one provider.
- **Alternatives:** Hono on Cloudflare Workers (no server to maintain, but runtime limits and harder to move on-site); NestJS (more ceremony); Supabase Edge Functions (vendor-specific).
- **Revisit if:** hosting moves to a serverless platform.

## D-03 · Database — Open (Q1)
- **Decision:** PostgreSQL 17 or newer, accessed through Drizzle ORM, with SQL migrations generated by drizzle-kit and committed.
  - **Path A (Oracle Ampere A1 VM):** Postgres runs in Docker on the same VM.
  - **Path B (1 GB E2.1.Micro VM):** managed Postgres. Supabase free tier, used as plain Postgres through its connection string (Neon is the alternative).
- **Why:** orders, items and payments are relational, and reporting needs SQL (`date_trunc`, window functions). Drizzle keeps the SQL visible and typed. Plain Postgres lets us move between Oracle, Supabase and a Mini PC.
- **Alternatives:** Firestore (realtime built in, weak for reports); SQLite/PocketBase (simple, fewer reporting tools); Cloudflare D1 (ties us to Workers).
- **Revisit if:** Q1 is answered (VM shape), or the database grows past the free limits.
- **PGlite version (2026-09-29, P1):** pinned to **0.4.x, which embeds PostgreSQL 17**, the same major as Supabase (17.6). PGlite 0.5.x embeds PostgreSQL 18, where migrations could use PG18-only features that then fail on Supabase. Upgrade PGlite only together with the Supabase major version. Migrations are plain SQL/plpgsql with no extensions, so the same set runs on both.
- **Status note (2026-09-29):** the VM is a **VM.Standard.E2.1.Micro (1 GB RAM) in ap-singapore-1**, so **Path B** applies. Postgres runs on Supabase free, created in the Singapore region next to the VM. Record: [infra/oracle/README.md](../infra/oracle/README.md).

## D-04 · Realtime sync — Accepted (built and deployed 2026-10-02)
- **Decision:** the server is the only source of truth. Every write goes through the API in a DB transaction. Each synced row has a `rev` taken from one global Postgres sequence. After commit the API broadcasts `{type, id, rev, data}` over WebSocket. A reconnecting client calls `GET /v1/sync?since=<rev>` to catch up. Creates carry an idempotency key, and updates carry `expectedVersion` (HTTP 409 on conflict).
- **Why:** it is simple, stays correct after disconnects, and does not depend on Supabase Realtime or Firebase.
- **Alternatives:** Supabase Realtime (lock-in; not available on Path A); CRDT/local-first sync (overkill for one shop).
- **Revisit if:** we run more than one API instance. Then add Postgres `LISTEN/NOTIFY` for fan-out.
- **Status note (2026-10-02, as built):** the WebSocket authenticates with a first message (a browser cannot send headers) and the server re-checks the session on every 25 s beat without extending it, so a listen-only device gets 4401 at its idle limit and the client must keep the session alive or re-sign-in. The feed uses column allow-lists per table and role permission (payments `payment.record`, settings `settings.view`, customers `customer.view`); costs, staff, devices, sessions, audit and expenses never travel and the PromptPay ID is masked. Clients apply a frame only if its `rev` is higher and rewind 200 revs once per catch-up, because a transaction that commits late can carry a lower `rev` than one already sent.

## D-05 · Frontends — Proposed
- **Decision:** React 19 + Vite + TypeScript, TanStack Router and Query, Tailwind CSS v4 + shadcn/ui (Radix), Apache ECharts for charts, i18next, `vite-plugin-pwa`, and Dexie (IndexedDB) for the offline outbox. Two apps:
  - `apps/pos-web`: every staff function (POS, order board, kitchen view, menu, payments, back office, settings), gated by role.
  - `apps/liff-web`: the customer app that opens inside LINE.
- **Why:** one staff app means one login, one realtime connection and one deploy. The customer app stays small for LINE's in-app browser.
- **Alternatives:** SvelteKit (smaller bundles, less familiar); Next.js (server rendering not needed); a separate back-office app (more to deploy).
- **Revisit if:** the back office grows large enough to split into `apps/admin-web`.
- **Status note (2026-10-01, from the QA review of the first staff-app slice):** the auth slice was built with a hash router, plain CSS on the `--sds-*` design tokens, a small custom translator in `packages/i18n` and a custom token store, and none of TanStack Router/Query, Tailwind, shadcn, i18next, `vite-plugin-pwa` or Dexie. That is acceptable for the sign-in screens (smaller bundle, hash URLs also suit Capacitor and Electron `file://` origins). **Four things must be decided before order entry and the offline outbox (P3 tasks 7 and 8):** (1) routing that can express `#/orders/:id` (the current `pathFromHash` matches one segment); (2) how server state is cached and invalidated by realtime events; (3) the IndexedDB layer for the outbox (Dexie or raw IndexedDB behind the platform seam); (4) an app-shell service worker, because an iPad that reloads while offline cannot load the app today, which conflicts with docs/02 section 8.
- **Status note (2026-10-02, the four items decided under the owner's standing authorization):** (1) **Routing:** keep the hash router and extend it to match parameterised paths such as `#/orders/:id`; no TanStack Router. (2) **Server state:** a small custom store keyed by entity id that applies an event only when `event.rev` is greater than the stored `rev` (02 §5), fed by the WebSocket and `GET /v1/sync?since=`; no TanStack Query, because per-entity `rev` ordering and catch-up are the cache rules. (3) **IndexedDB for the outbox:** Dexie, wrapped behind the platform seam (`apps/pos-web/src/platform/`) so features never import it and the native shells can swap the implementation. (4) **App-shell service worker:** `vite-plugin-pwa` (Workbox) precaching the app shell only, with a navigation fallback and no caching of `/v1` responses; registration sits behind the platform seam because service workers do not run on Electron `file://` origins and are often unavailable in Capacitor. Tailwind, shadcn and i18next stay out (plain CSS on the design tokens and the `packages/i18n` translator remain).

## D-07 · Manual payment confirmation — Accepted (owner requirement)
- **Decision:** staff confirm every payment by hand. They count cash, and they check PromptPay or government co-pay money in the bank or ถุงเงิน app. A customer can tap "โอนแล้ว" (I've paid) and attach a slip, but that only moves the payment to *awaiting confirmation*. There is no payment gateway and no paid slip-verification API.
- **Why:** there are no transaction fees and no provider dependency.
- **Revisit if:** volume makes manual checking a bottleneck. The option then is a bank merchant QR with an API; fees apply.

## D-08 · Government co-pay method — Proposed (depends on Q2)
- **Decision:** a generic payment method, "โครงการรัฐร่วมจ่าย", preset for **ไทยช่วยไทย พลัส 60/40**. It has configurable name, government share, daily cap, active dates and hours, and allowed channels. It is **disabled outside those dates and hours**. The customer pays **face-to-face at the storefront** by scanning a QR that staff create **per transaction** in ถุงเงิน. The QR is **never sent through LINE**. LINE customers can pick it as "pay at the storefront".
- **Why:** the scheme rules require per-transaction QRs, scanning at the storefront and GPS (see [04-integrations.md](04-integrations.md#3-government-co-pay-scheme-thai-chuay-thai-plus)). Schemes also change name and ratio every few months.
- **Revisit if:** the scheme's terms allow remote payment.
- **Owner decision (2026-10-02):** the shop delivers only to the building entrance (a security guard is stationed there) and the customer comes down to receive the order, so the hand-over is face to face. Co-pay is therefore offered for `entrance_delivery` orders as a plain payment option: staff create the ถุงเงิน QR for the transaction at the hand-over, the customer pays, and **staff confirm it by hand**, exactly like PromptPay. It stays refused for `platform_delivery`, `grab` and `lineman` orders, outside the scheme dates and hours, and when disabled; the QR is never sent through LINE. ⚠ Compliance risk accepted by the owner: whether the scheme's terms (face-to-face scan, GPS at the shop) allow a hand-over at the building entrance is **not confirmed with ถุงเงิน**; if the terms or an audit say no, switch the scheme off in settings.
- **Channels (2026-10-02):** co-pay is refused for `grab` and `lineman` orders (the platform takes the payment) as well as room and platform delivery; a LINE pickup order paid at the counter stays allowed, because that payment is face to face.

## D-09 · LINE messaging budget — Proposed
- **Decision:** anything the customer triggers gets a **reply** (free). After ordering, the customer app calls `liff.sendMessages()` so the order summary and QR go out as a free reply. **Push** messages, which count against the quota, are used only for "order ready" and for messages staff start themselves. A quota tracker holds a policy switch (`always` / `ready-only` / `off`) and warns at 80%. Customer questions are answered by hand in the LINE OA Manager chat, which is free.
- **Why:** the Thailand free plan counts 300 push/multicast/broadcast/narrowcast messages a month. Replies, chat and auto-responses are not counted.
- **Revisit if:** LINE orders pass about 250 a month. Then upgrade to the Basic plan (฿1,280/month for 15,000 messages as of Sept 2026).

## D-11 · Money and time — Proposed
- **Decision:** amounts are stored as integer **satang** (`bigint`), in THB only. The server always computes totals. Timestamps are stored as `timestamptz` in UTC and shown in Asia/Bangkok time. Reports group by `business_date`, whose cutoff is configurable (default 04:00, so late-night sales count for the previous day).
- **Why:** no floating-point rounding errors, and daily totals are correct even if the shop closes after midnight.
- **TypeScript representation (2026-09-29, P1):** in code, satang is a branded `number` that must be a safe integer (`Number.isSafeInteger`, ±9×10¹⁵ satang), not JS `BigInt`. The DB column stays `bigint`, read by Drizzle in `number` mode. Why: `BigInt` cannot go through `JSON.stringify`, Zod-over-HTTP or React without custom serialization, and the shop's amounts are many orders of magnitude below the limit. Guards in `packages/shared/money` reject non-integers and unsafe values.

- **Decision:** pg-boss, a Postgres-backed queue and cron, runs inside the API process. Jobs include overdue-payment reminders, the daily summary, quota checks, retention cleanup and print-job retries.

## D-17 · Staff authentication — Proposed
- **Decision:** the owner registers each device once, which issues a long-lived device token that can be revoked. Staff unlock with a personal 4–6 digit PIN (hashed, rate-limited, locked after repeated failures). Roles are owner, manager, cashier and kitchen. The owner's back-office login uses a password plus TOTP. Sensitive actions (**changing the PromptPay ID**, managing staff, voiding a paid order, exporting data) ask for the password again.
- **Proposed amendments from the first build slice (2026-10-01, status stays Proposed; some items are in review):**
  - **Tokens and sessions:** opaque 256-bit random bearer tokens stored only as SHA-256; sessions are database rows, so a revoke or a role change takes effect at once. PIN sessions last 12 h (idle 2 h), owner sessions 8 h (idle 30 min), and PIN sessions are bound to the registered device.
  - **Step-up follows the role, not how the session was opened:** the owner gives password plus a TOTP or recovery code, even on a device unlocked with a PIN; other roles re-enter their PIN. Signing in does not count as step-up. A step-up lasts 5 minutes.
  - **Secrets at rest:** passwords and PINs use scrypt (PINs also peppered with a key derived from `AUTH_SECRET_KEY`); the TOTP secret is AES-256-GCM encrypted under that key; recovery codes are single-use. TOTP is RFC 6238 with a plus/minus one step window and replay protection.
  - **Locks:** 5 wrong PINs lock for 5 minutes, escalating to 1 hour and 24 hours on repeated lock cycles; PINs for the owner and managers are 6 digits; the owner account locks for 15 minutes after 5 wrong tries, with separate counters for public sign-in and step-up so a stranger cannot keep the owner out of sensitive actions.
  - **Master key:** `AUTH_SECRET_KEY` lives only in the VM `.env` plus an offline copy; the API refuses to start without it; it must never be regenerated on a rebuild or rotated to sign devices out.

## D-18 · Backups and monitoring — Proposed
- **Decision:**
  - Hourly `pg_dump` during opening hours plus a nightly full dump. Dumps are encrypted with `age` and stored in OCI Object Storage (see the status note: R2 dropped). A healthchecks.io ping fires if a backup is missed.
  - An external uptime check on `/healthz`, and Sentry's free tier for errors.
  - A restore drill every month.
- **Targets:** at most 1 hour of data lost (RPO), and back online within 2 hours (RTO).
- **Status note (2026-09-29, P2 kickoff):** the owner chose **OCI Object Storage only** for backups (no card at Cloudflare, so no R2). Risk accepted: the VM and the backups are with one provider. Mitigation to consider: a weekly automatic copy to the owner's laptop. The age private key is kept printed plus on a USB drive (no password manager yet).

## D-19 · Client platforms and the native path — Proposed (depends on Q13)
- **Now (P3–P5), web first:**
  - Staff use `pos-web` in **Safari on iPad and iPhone** and in standard desktop browsers (Chrome, Edge, Firefox, Safari on macOS).
  - Staff devices should use **Add to Home Screen**. It is still Safari, but runs full screen, can receive Web Push (iOS 16.4+), and is exempt from Safari's rule that deletes a site's stored data after 7 days without use.
  - A plain Safari tab also works, with those limits (see [02 §12](02-architecture.md#12-client-platforms-and-the-native-path)).
- **Later (P10), native installable apps built from the same React code:**
  - **iPad and iPhone: Capacitor** (`apps/pos-mobile`). It has an official push-notification plugin, keep-awake and secure storage, and community TCP/ESC-POS plugins for printing to the LAN printer from iOS.
  - **Windows, macOS and Linux: Electron** (`apps/pos-desktop`). Its Node main process can reuse `packages/escpos` (TypeScript) to print directly over LAN or USB. It uses the same Chromium engine on all three systems, so Thai text renders the same everywhere.
- **Built now so the native step stays cheap:**
  - the API base URL is set by config (no same-origin assumption);
  - login uses bearer tokens, not cookies (already D-17);
  - the CORS allow-list is configurable, so native app origins can be added later;
  - a thin platform interface in `pos-web` (sound/notifications, wake lock, token storage, print) has **web implementations only**.

  No other native work happens before P10.
- **Why:** one UI codebase for five platforms, with the web version live from day one.
- **Costs and blockers, for the owner to decide (Q13):**
  - iOS distribution (TestFlight, Ad Hoc, Unlisted or App Store) and macOS notarization require the **Apple Developer Program, US$99 a year**.
  - iOS and macOS builds need **macOS + Xcode**, and the owner currently works on Windows.

## D-20 · Offline PromptPay — Accepted (owner decision 2026-10-02)
- **Decision:** a staff device keeps the **real PromptPay ID** in the local store (IndexedDB, never the token store, never the outbox) so a PromptPay QR can be drawn offline with `packages/promptpay`. The ID is read from `GET /v1/settings/promptpay` (roles with `settings.view`) after every sign-in, on reconnect and on every `settings.updated` for `promptpay`, and is cleared when a different staff member signs in on the device or the device is revoked. An offline PromptPay payment is queued like cash (create pending, then the staff member's confirm after checking the bank app), so **staff still confirm every payment by hand** (rule 2).
- **Why:** the exit criterion says "cash and PromptPay still work with the internet unplugged", and the shop's internet is the weakest link.
- **Risks the owner accepted, and the mitigations:** (1) a device that is offline when the owner changes the ID keeps showing the OLD account's QR: the QR screen shows when the ID was saved and tells staff to compare the masked account with the bank app, the owner's change alert is the signal to refresh every device, and a QR is refused once the saved ID is older than a limit (default 24 h) until the device reconnects; (2) a stolen unlocked device exposes the ID (it is on every printed or shown QR anyway; revoke the device); (3) the offline amount is an ESTIMATE from the cached menu, so the QR amount can differ from the server total if prices changed: the screen says so and a mismatch at replay ends as 'needs attention'. Not allowed offline: co-pay (staff create the ถุงเงิน QR in their own app and the system cannot check the scheme window against the server), changing the PromptPay ID, and order moves.
- **Revisit if:** the owner prefers 'cash only offline', or a bank offers a merchant QR that does not need the ID on the device.

## D-21 · Menu photos in Postgres — Accepted (2026-10-02)

## D-24 · Transfer slip images on the VM disk — Accepted (owner delegated the choice, 2026-10-11)
- **Decision:** a slip is a JPEG, PNG or WebP of at most 5 MB, stored as a file under a random 32-character key in `SLIP_DIR` (a named Docker volume on the VM, `slips_data`). The database keeps only the key (`payments.slip_image_key`), never in DTOs, realtime frames or sync. The code reaches the files through a small `SlipStore` interface (put, get, delete), so a bucket can replace the disk later. A slip only makes the payment `claimed` (D-07); staff confirm.
- **Retention:** 90 days after the payment was confirmed (or, for cancelled, voided and refunded payments, last changed), by a nightly job (`retention-slips`) that deletes the file first and clears the key after. A file that cannot be deleted keeps its key and is tried again the next night.
- **Access:** customers upload only to their own order's pending or claimed PromptPay payment (a second upload replaces the first). Staff with `payment.record` view it with `Cache-Control: private, no-store` and `nosniff`; every view writes an `audit_log` row.
- **Why:** no new service, secret or cost (rule: free tier); a slip shows a customer's bank app, so it stays off the database backups' off-site copies unless the owner decides otherwise.
- **Alternatives:** Postgres `bytea` (D-21 style; fills the free database and its backups), Supabase or Cloudflare R2 storage (a new credential and, for R2, a payment method).
- **Revisit if:** the VM disk is lost or rebuilt (slips are NOT in the hourly database dump: a restore drill that must keep slips needs the `slips_data` volume copied too), or volume grows past what the VM disk can hold.

## D-25 · Partial adjustment of a paid order — Accepted (owner decision 2026-10-11)
- **Context:** an owner edit that changed the total of an order with a confirmed payment could only void or refund the whole payment and collect again.
- **Decision:** `PATCH /v1/orders/:id/correction` takes `paymentAction: 'adjust'` (besides `void` and `refund`, which work as before; the void endpoint keeps its own two-value enum).
  - **Lower total:** the confirmed payment stays `confirmed`; the difference is recorded as an append-only row in the new table `payment_refunds` (`payment_id`, `amount_satang > 0`, `method` cash or promptpay, `reference_note`, `reason`, staff, time). The owner sends only `refund: {method, referenceNote?}`; the server computes the amount (newest payment first, never more than is left on one). Only cash and PromptPay payments can be partly refunded.
  - **Higher total:** nothing is created. The order becomes `partially_paid` and staff take the difference with the normal `POST /orders/:id/payments`, which now charges `total − net paid` (so the PromptPay QR, the cash change and the co-pay split use the exact difference). Staff still confirm by hand; nothing is confirmed automatically.
  - **Net paid** = confirmed amounts − their partial refunds. `derivePaymentStatus` uses it, and so must every report: revenue is net paid; voided orders are excluded; a whole refund after partial ones returns only `amount − partials`.
- **Why the state machine is not changed:** no payment moves to another status, so there is no transition to add. Who may do it is the machine's own `confirmed → refunded` rule (manager or owner, reason, step-up), asked as a probe. The route is owner-only with a fresh step-up, writes `payment.partial_refund` audit rows and sends a critical owner alert.
- **Refusals (409):** a claimed payment (`ADJUST_CLAIM_OPEN`: confirm or cancel the claim first), a new total of zero (`ADJUST_TOTAL_ZERO`), money to return that sits on a co-pay, platform or other payment (`ADJUST_METHOD_NOT_ADJUSTABLE`). 422: `REFUND_DETAILS_REQUIRED`, `REFUND_NOT_NEEDED`.
- **Not synced:** `payment_refunds` has no `rev`; devices read it, with `netPaidSatang` and `dueSatang`, from `GET /v1/orders/:id/payments` when `order.upserted` arrives.
- **Customer notice:** after an owner void or an edit that changes the items or the total, a LINE order gets one text push (order number, what happened, new total, refund or amount due) through the quota-aware sender, counted as `essential`; template `order_void`, or `order_edit:<version>` so each edit is its own message. Exhausted quota or policy `off`: skipped, no error.
- **Member profile retention:** nightly job `retention-member-profiles` clears full name, nickname, phone and member building of customers with no order for 24 months (730 days); the customer, LINE id and history stay; audit row with counts only.
- **Revisit if:** the owner wants partial refunds of co-pay money, or receipts for orders with a top-up (a receipt picks one confirmed payment today).

## D-26 · Reading the amount on a slip with local Tesseract — Accepted (owner decision, 2026-10-11)
- **Decision:** after a slip is stored (D-24), the API reads the amount on the picture with **Tesseract OCR running inside the api container on the VM** (`tesseract-ocr`, `-tha`, `-eng`; `tha+eng`, one thread, `nice`, one picture at a time, killed after 60 s). The result is a **hint for staff, never a decision**: it does not confirm, reject or block a payment (rule 2). The payment stays `claimed` until staff confirm from the bank app.
- **What is kept:** `payments.slip_amount_satang` (the amount read, or null) and `payments.slip_check` = `pending` | `match` | `mismatch` | `unreadable` (null: no slip, or the reading is off), compared with **this payment's** amount (a top-up payment charges only the difference). **The OCR text is never stored or logged** (it holds names and account numbers); the reader's output is parsed and dropped. A new slip resets both fields; the 90-day purge and a customer erasure clear them with the key.
- **How it runs:** in the API process, after the claim commits, through a one-at-a-time queue, plus a per-minute sweep job (`slip-check-sweep`) for a restart or a full queue. It never delays or fails the upload. Pictures whose header size is unknown or above 16 million pixels are not read (`unreadable`), so a small file cannot make the 1 GB server decode a huge picture. When the result lands the payment gets a new `rev` (so devices ask again), but the hint is not in the payment DTO, realtime frames or sync: staff get it from `GET /v1/orders/:id/payments` (`slipChecks`), like the slip ids (D-24).
- **Staff screen:** a banner (green match, amber mismatch, grey unreadable) that says it is automatic and the bank app still decides, a small chip, and on a mismatch the confirm button needs a second explicit tap. The fake-slip warning stays.
- **Customer app:** the customer can look at the slip they sent (`GET /v1/app/orders/:id/slip`, own order only, no-store, rate limited, no audit row) and replace it. The reading is never shown to them.
- **Duplicate-slip hint (2026-10-13, migration 0028):** staff are told when a slip was used before. Still a hint, never a rejection: the claim goes through as `claimed` and staff confirm by hand (rule 2).
  - **What is kept:** `payments.slip_image_hash` (SHA-256 hex of the picture's bytes, set when the slip is stored) and `payments.slip_ref_hash` (SHA-256 of the normalised bank reference, set by the reading job). Only hashes, indexed; never the reference or the OCR text. The reference is read by a pure parser (`extractSlipRef`: รหัสอ้างอิง, เลขที่รายการ, Ref, Transaction ID; at least 10 characters with 6 digits; two different references or no label gives null). A new slip resets both hashes; the 90-day purge and a customer erasure clear them with the key.
  - **Rule:** a slip is a duplicate when ANOTHER payment (any order, same order too) that was claimed EARLIER has the same image hash or the same ref hash and is `claimed`, `confirmed` or `refunded`. `pending` has no slip; `cancelled` and `voided` payments do not count (their slip was rejected or taken back). The identical file sent again for the same payment is not a duplicate. The earliest match wins.
  - **Where:** computed when staff read `GET /v1/orders/:id/payments`, so a reference read a moment after the claim is included. It is a separate list `slipDuplicates: [{paymentId, orderNo, paymentStatus}]` (the earlier order's number and its payment status only), apart from `slipChecks`, so the amount check is untouched and a duplicate also shows when the reading is off.
  - **Staff screen:** a strong red banner above the amount banner ("สลิปนี้เคยใช้แล้วกับออเดอร์ L-xxx (สถานะ ...)", says it is automatic), a red chip, and confirm needs the same extra tap as a mismatch (one extra tap covers both warnings). **Customer app:** nothing new; other orders are never revealed.
  - **Limits:** the picture hash catches only the same file bytes: a re-photographed, screenshot, re-compressed or edited slip gets a different hash and is caught only if the reference is read (OCR may fail; the reference is not read when the reading is off). A fake slip with an invented reference is not caught. The first claim of a pair is not flagged (only the later one). Order is by claim time.
- **Small QR on the slip (2026-10-13, migration 0029):** Thai bank slips print a small "slip verify" QR (TLV: API id, sending bank code, transaction reference). It is decoded **on the VM** and its reference becomes the strongest duplicate key: a screenshot or a re-photo has another picture hash and OCR may not read the printed reference, but the QR is the same. Still a hint, never a decision (rule 2).
  - **What is kept:** only `payments.slip_qr_hash` (migration 0029, indexed) = SHA-256 of `sendingBank:transRef` (normalised: upper case, no hyphens). The QR text, the bank code and the reference are never stored or logged; the worker answers with the parsed pair and the checker hashes it at once. Null when no readable slip QR was found. A new slip resets it; the 90-day purge and a customer erasure clear it with the key; it is excluded from sync like the other slip columns.
  - **Why a separate column and not `slip_ref_hash`:** the QR reference is hashed together with the bank code, the OCR reference is the printed text alone, and the two may even differ on some banks (the printed "รหัสอ้างอิง" is not always the QR's transaction reference), so they are not comparable. The duplicate rule matches on ANY of image, ref or qr hash (same status rules as before); the answer says what matched (`matchedBy`: qr, then ref, then image) and the staff banner then reads "รหัสอ้างอิงในคิวอาร์สลิปตรงกับสลิปเดิม". A slip QR and a printed-only reference of two different slips of one transfer are NOT linked to each other.
  - **Parser (`packages/shared/src/slip-qr.ts`, pure):** strict TLV (2-digit tag, 2-digit length, nothing left over); a nested block with 00 = API id (6 digits), 01 = sending bank (3 digits), 02 = reference (same normalisation as `extractSlipRef`); a CRC tag 91, when present, must be last and match CRC-16/CCITT-FALSE (a small local copy: `@sds/promptpay` depends on `shared`). Two different blocks, any odd length or a bad CRC give null.
  - **Decoding (`apps/api/src/slips/qr*.ts`):** `jsqr` 1.4.0 (Apache-2.0, pure JS; the pos-web scanner already uses it), `jpeg-js` 0.4.4 (BSD-3-Clause) and `pngjs` 5.0.0 (MIT): pure JavaScript, no native module, no `sharp`, nothing to compile for the ARM image. It runs in a **worker thread** (one picture per worker, only when the checker asks, so one at a time): CPU work must not stop the API, and a hard 20 s timeout terminates the worker (the decoder also stops between tries after 15 s). The size guard (header size known and at most 16 million pixels) runs BEFORE any decoding; the decoders also refuse over 16 MP / 256 MB. It runs inside the existing reading job, first, so the upload never waits and an OCR failure still leaves the QR key. Tries (bounded to 4): the whole picture, the lower half, the lower right, the centre, each shrunk to at most 3 million pixels (a crop is read at full resolution).
  - **Staff screen:** a neutral grey note "ไม่พบคิวอาร์บนสลิป" when the reading finished and no QR was found (`slipChecks[].qrFound`); it is not an alarm and changes nothing about confirming.
  - **Limits (honest):** the QR is read only if the picture is sharp enough and large enough (a blurry or tiny photo, a QR cut off, a screenshot shrunk by a chat app: no key); WebP slips are not decoded; JPEG/PNG only. A **fake slip with a made-up QR is not caught**, and a real QR on a doctored slip still reads. **This does not prove that money arrived**: only the bank app, or a paid verifier of the bank's own API, can say that. Only the layout "API id, bank, reference [, country] [, CRC]" is known from public documentation; the other layouts in the tests are synthetic, and no real slip was available to check them, so real-slip accuracy is **not measured yet** (measure after deploy; banks that put extra fields or another structure would give null, never a wrong key). The decoding timeout is a hard stop for the worker; a worker uses extra memory while it runs (an unmeasured estimate for a 12 MP JPEG is 150 MB or more; measure after deploy), so `SLIP_QR=off` is the first switch to try if the 768 MB container gets tight.
  - **Switch / deploy:** `SLIP_QR` (`off`, or on; default on whenever the slip reading is on, so production only). **No Dockerfile change**: the dependencies are bundled by esbuild, plus one more bundle entry, `dist/slip-qr-worker.js`, which the existing `COPY dist` already ships. `pnpm install` picks up `jsqr`, `jpeg-js`, `pngjs` (lockfile updated); migration 0029 is additive (expand only).
- **Receiver check (2026-10-11, migration 0030):** a genuine slip of a transfer made to SOMEONE ELSE with the same amount passed the amount check and is not a duplicate. The reading job now also reads the receiver block and compares it with the shop's PromptPay ID. Still a hint, never a decision (rule 2): nothing is confirmed or rejected.
  - **What is kept:** only `payments.slip_recipient_check` = `match` | `mismatch` | `unknown` (CHECK constraint; null = not read: no PromptPay ID in settings, the reading is off, or the picture was unreadable). Never the text, the receiver's digits or name. The ID is read from settings (`currentPromptpayId`) when the slip is checked, never hardcoded; changing the ID later does not re-check old slips. A new slip resets it; the 90-day purge and a customer erasure clear it with the key; it is excluded from sync, not in the payment DTO or realtime frames, and not shown to customers. Staff get it from `GET /v1/orders/:id/payments`, `slipChecks[].recipientCheck` (omitted when null).
  - **Parser (`packages/shared/src/slip-recipient.ts`, pure):** only lines in the receiver's block count (a line opening with ไปยัง / ผู้รับ / ถึง / To / Receiver / Payee / Biller, and the next 4 lines, ended early by a field such as จำนวน, ค่าธรรมเนียม, รหัสอ้างอิง, วันที่). The sender's block (จาก / ผู้โอน / From / Sender / Payer) is never compared; a line that holds both kinds of label (a merged column) is skipped. Thai digits are read. A masked number (`xxx-xxx-4567`, `08x-xxx-4567`, `***`, bullets, `+66 8x xxx 4567`, `x-xxxx-xxx90-12-3`) must have the shape of the shop's ID type (phone 3-3-4, national ID 1-4-5-2-1, e-wallet 15 characters; an unseparated number needs a mask character, because a bare digit string may be a reference). A bank account number (3-1-5-1) is NOT comparable with a phone or national ID.
  - **Rules (conservative on purpose):** `match` = every visible digit equals the ID at the same position AND at least 4 visible digits beyond the common leading ones (a phone's first 2, a national ID's first 1, an e-wallet's first 3): 4 digits are a 1-in-10,000 coincidence for another person, while the leading digits (`08`) carry almost none. `mismatch` = the same amount of evidence (at least 4 informative visible digits) with at least 2 visible digits in conflict, so one OCR misread cannot flag a genuine slip. Everything else is `unknown`: no receiver block, hidden or too few digits, one conflicting digit, a number of another shape, two receiver numbers that disagree.
  - **Staff screen:** `mismatch`: a red banner above the amount banner ("ผู้รับบนสลิปดูไม่ตรงกับบัญชีร้าน — อาจโอนให้คนอื่น ตรวจในแอปธนาคารของร้าน", says it is automatic) and a red chip; confirming needs the SAME single extra tap as an amount mismatch or a duplicate (one tap covers all warnings; every warning shows). `unknown`: a small neutral note. `match`: a small green chip that says it is an automatic hint. The fake-slip warning stays.
  - **Limits (honest):** banks mask differently and some slips show the receiver's BANK ACCOUNT instead of the PromptPay proxy, which cannot be compared (then `unknown`: expect many `unknown`); OCR may misread digits or lose the receiver label; the receiver's NAME is not compared (the shop's name is not in settings and Thai names OCR badly); a `match` shows only that the printed receiver looks like the shop's ID, it does NOT prove the money arrived (a slip can be fake or edited): staff must still look at the incoming-transfer notification in the shop's bank app. Accuracy on real Thai slips is not measured yet.
  - **Revisit if:** real slips show `unknown` most of the time (add the receiving bank's account number as an optional setting, or compare the name), or `mismatch` fires on genuine slips (raise the evidence needed).
- **Stricter confirm and the shop receiving account (2026-10-11, no migration):** a slip sent to ANOTHER person or bank with the same amount still got through, because the receiver check often answered `unknown`. Two changes. Still only a hint: it does not prove that money arrived; the incoming transfer in the shop's bank app is the real proof (rule 2 unchanged: staff confirm by hand and the server never blocks on any of this).
  - **Confirm rule (staff screen only; replaces the "one extra tap" of the amount, duplicate and receiver warnings above):** when a PromptPay payment has a slip and the receiver check is anything but `match` (mismatch, unknown, not checked), or the amount check is anything but `match` (mismatch, unreadable, pending, not read), or a duplicate is flagged, the confirm button stays off until staff tick "ฉันตรวจยอดเงินเข้าในแอปธนาคารของร้านแล้ว" (amount, time, reference). One tick replaces the extra tap: one clear step, not two. Only receiver `match` AND amount `match` AND no duplicate keeps the plain one-tap confirm. A payment without a slip (staff checked the bank app themselves, or cash) keeps today's flow. If the slip list cannot be read, the screen asks for the tick (fail closed). The tick starts over when the payment's revision changes (a new slip or reading).
  - **Audit:** the confirm request carries `attestedBankCheck: true` (only ever `true`, only when the tick was needed). The server writes it into the `payment.confirm` audit row's `after` and does nothing else with it: no block, no extra check. The gate is UI-only by design (a malicious client could skip it, but it can already confirm without a slip; the audit row shows who ticked).
  - **New setting `bank_account` (`GET/PATCH /v1/settings/bank-account`, optional):** the shop's receiving bank account number (10 to 15 digits) and an optional bank from a small fixed list (BoT codes 002 BBL, 004 KBank, 006 KTB, 011 TTB, 014 SCB, 025 Krungsri, 030 GSB, 034 BAAC; informational only). Same protections as the PromptPay ID and the receipt settings: permission `settings.bank_account` (owner only), fresh step-up, audit row `settings.bank_account_change` with only the bank code and the masked number (last 4 digits), a `warn` alert to the owner (`settings.bank_account_changed`), `expectedVersion` (409 on a stale one). **The full number never leaves the server:** GET and the PATCH answer give only `{bankCode, accountMasked, configured}`; roles without the permission get only `configured`. It is not in `SYNCED_SETTING_KEYS` (so not in sync), emits no `settings.updated` frame, and no log, audit row, alert or notification holds it. The settings screen (owner only, `#/settings/bank-account`) shows the masked account, never fills the number back, and clears it with a "remove" button.
  - **Comparison (`packages/shared/src/slip-recipient.ts`):** `checkSlipRecipient(text, promptpayTarget | null, account | null)`. A receiver number that fits the PromptPay ID's shape is judged only against the ID, as before. Otherwise a number grouped into 3 or more groups that is not a phone's (3-3-4) or national ID's (1-4-5-2-1) grouping, or a masked unseparated string of a length no phone or ID has (not 10, not 13), with exactly the configured number of digits, is judged against the account with the same conservative rules (at least 4 visible digits beyond the first 3, which are branch digits; `mismatch` only with at least 2 conflicting visible digits; else `unknown`). A phone-, ID- or `+66`-shaped receiver is never compared with the account, and an account-shaped one never with the PromptPay ID; a fully visible unseparated digit string is ignored (it may be a reference). A different length is `unknown` (it cannot be aligned). Only the receiver's block is read, as before. The checker reads both settings at check time (a damaged account row means "no account", it never breaks the PromptPay comparison); the result is still the single stored enum `slip_recipient_check`, so no migration.
  - **Limits (honest):** many banks mask the account to 3 or fewer visible digits (for example `xxx-x-xx123-x`), which stays `unknown`; OCR can misread digits; the receiver's name is not compared; a doctored or fake slip can show the right receiver. That is why the tick exists: a slip is never proof.
- **Why local Tesseract:** free, no new service, secret or quota, and a slip never leaves the shop's server (PDPA: a bank name, account number and the customer's name).
- **Why not Gemini or another cloud model (incl. Antigravity):** it would send every customer's bank details to a third party, and needs a key and a quota. The shop's own server keeps the picture.
- **Switches:** `SLIP_OCR` (`off`, or on; default on in production only), `SLIP_OCR_LANG` (`eng` is lighter), `SLIP_OCR_TIMEOUT_MS`.
- **Risks:** accuracy on real Thai bank slips is **not measured yet** (no real slips were available); the VM is an E2.1.Micro (1 GB, 1/8 CPU), so one reading may take tens of seconds and the container's 512 MB limit must be checked (Node heap 384 MB plus Tesseract). Both are measured after deploy; the switch lets the shop turn it off.
- **Revisit if:** accuracy is poor (try `eng` only, or a pre-resize step), the reading is too slow or kills the container, or the shop moves to a bigger VM.

## D-29 · How a feature folder in `apps/api/src` is laid out — Accepted (architecture refactor, owner-approved plan 2026-10-16)
- **Layers inside `apps/api/src/<feature>/`:** `routes.ts` (HTTP and Zod at the edge) → use-case files, one per group of use cases (for payments: `create.ts`, `moves.ts`, `read.ts`, …) → `@sds/db` repositories → `@sds/shared` pure rules. A feature's `internal.ts` holds what its own use-case files share and imports nothing from them, so no cycle can start there.
- **`service.ts` is the feature's interface:** a barrel that re-exports the use cases. Other features import only from `service.ts` (or `dto.ts`), never from a use-case file or `internal.ts`.
- **The refactor only moves code.** Function bodies do not change; the old path stays as a barrel. A duplicate helper is merged only if its copies are identical apart from names. The three `request-hash.ts` files stay separate on purpose: merging them would change stored fingerprints and make replays fail with `IDEMPOTENCY_KEY_REUSED`.
- Replaces the `src/modules/` layout drawn in the first version of `02-architecture.md`; the references in `CLAUDE.md`, `02-architecture.md`, `04-integrations.md` and the LINE agent definition now say `src/<feature>/`. The same layout idea was applied to `packages/db/src/schema/`, `packages/i18n/src/{th,en}/`, `apps/pos-web/src/api/{http.ts,resources/}`, `apps/liff-web/src/ui/order/` and `apps/pos-web/src/pos/<feature>/`.
- Not enforced by a lint rule; it is a convention. A later `dependency-cruiser` or Biome `noRestrictedImports` rule could enforce "other features import only `service.ts` or `dto.ts`".

## D-32 · P7 item costs: "no cost entered" is NULL, margin over costed data only, commission rate vs recorded commission — Accepted (set by Claude on 2026-10-20 from the owner's P7 answers; owner approved 2026-10-21)
- **The problem.** `menu_items.est_cost_satang` and `order_items.unit_cost_satang` were `NOT NULL DEFAULT 0`, so "the owner has not typed a cost" and "this item really costs nothing" were the same number, and a report would have shown a 100% margin for every uncosted dish.
- **Fix (migration 0038, forward-only).** Both columns drop `NOT NULL` and the default. **`NULL` = no cost entered; `0` = a real cost of nothing.** The same migration turns the stored zeros into `NULL` (`UPDATE menu_items SET est_cost_satang = NULL WHERE est_cost_satang = 0`, and the same for `order_items.unit_cost_satang`): until now a zero could only mean "not entered", and costs above 0 are untouched. The `menu_items` update bumps `rev`/`version` of the rows it changes like any menu edit; `order_items` is not a synced table. If the owner had deliberately saved a 0 before today, it reads "no cost entered" and must be typed again.
- **Option costs stay as they are.** `modifier_options.cost_delta_satang` is a *change* per unit (0 = no extra cost, a common and real value), so it stays `NOT NULL DEFAULT 0`. A cost of an extra only counts on top of a known item cost.
- **Snapshot.** `priceOrder` saves `unit_cost_satang = item cost + Σ option cost changes`, or `NULL` when the item has no cost. The snapshot is what reports use, never today's menu. **Historical orders are not re-costed from the current menu** (that would invent the cost of a sale): a line sold before its item had a cost stays "no cost entered" forever. A tool to cost the past from today's costs is possible later; it is a decision for the owner and is not built.
- **Menu editing.** The staff menu editor already had the cost fields (roles with `report.view`). The item cost box now means: blank = no cost entered (`PATCH estCostSatang: null`; a create without a cost saves `NULL`), `0` = a real zero. An item without a cost shows "no cost entered" in the list. The costs read (`GET /v1/menu/costs`) returns `null` for such an item. Costs still appear in no other response.
- **Item margin (`@sds/finance` `itemSales`).** Per item over counted orders: `costedQty` (units that have a snapshot), `costedRevenueSatang` (their line totals), `costSatang` = Σ unit cost × qty, `grossProfitSatang` = costed revenue − cost, `marginBp` = profit / costed revenue. Units without a cost are left out of all four, so an item sold partly before its cost was entered shows the margin of its costed units and `qty - costedQty` units uncosted. An item with no costed unit has `null` cost, profit and margin. The items answer also lists `uncostedMenuItemIds` (items with at least one uncosted unit). Like item revenue (D-30), these are line totals: an order discount or partial refund is not spread over items.
- **Period margin (`periodMargin`, in `revenue` answer `margin`).** Only **whole orders whose every line has a cost** are costed (an order with no lines is not). For those: revenue = net paid (the §6 revenue rule), cost = Σ unit cost × qty, `grossProfitSatang` = revenue − cost, `marginBp` = profit / revenue. A discount or refund lowers revenue but not cost (the food was made). Other counted orders are left out and named: `uncostedOrderIds`, `uncostedRevenueSatang`, `uncostedMenuItemIds`. Gross profit is **before** platform commission and expenses. Nothing is guessed or filled in.
- **Margin rounding.** `marginBasisPoints` in `@sds/shared` (half away from zero, so a loss and a profit of the same size round alike; `null` when revenue is 0). It is the only margin rounding rule, like `applyBasisPoints` for rates.
- **Platform commission (Grab, LINE MAN) in reports.** Per counted order: (1) a commission **recorded** on the order (`orders.platform_commission_satang`, 0 included) is the actual figure and always wins; (2) else for a Grab or LINE MAN order, estimate = net paid × that platform's `grabRateBp`/`linemanRateBp` from settings, rounded half up (`applyBasisPoints`); (3) else, with no rate set, the order has no commission number: it is named in `rateNotSetOrderIds` and its platform in `ratesNotSet`, and the total does not include it. **No built-in rate** (D-31). Other channels are never estimated. The `revenue` answer's `commission` block shows recorded and estimated sums, counts and the not-set list; `totals.commissionSatang` and each day's `commissionSatang` keep meaning "recorded on the orders" (so P6 figures and the CSV do not move). Nothing writes `platform_commission_satang` yet, so today every platform commission is an estimate or "rate not set"; a later step can record the real amount from the platform statement.
- **Not decided:** costing the past from today's costs; margin in the CSV exports (the files are unchanged); a margin screen (the answers carry the numbers, no screen shows them yet); recipe/ingredient costing (P7 later).

## D-33 · P7 profit and loss: one revenue base, a `complete` flag, the larger of commission and `platform_fees`, the larger of cost of goods and `ingredients`, owner only — Accepted with amendments (set by Claude on 2026-10-20; owner approved 2026-10-21 with the larger-of rules below)
- **Endpoint and who sees it.** `GET /v1/reports/pnl?from&to` (same range rules as the other reports: at most 366 days, `no-store`) needs the new permission **`finance.pnl`: owner only, no step-up** (read only, like `customer.report`). Managers enter expenses (`expense.edit`) but do not see profit (owner's kickoff default 10). Figures are an estimate for the owner, not a filing; income tax is a later part.
- **Lines (pure, `@sds/finance` `profitAndLoss`).** Revenue = net paid (03 §6, `revenueByDay`) over all counted orders. Cost of goods = `periodMargin` cost, i.e. only orders whose every line has a cost (D-32). **Gross profit = revenue - cost of goods** on that full revenue. Commission = `platformCommission` (recorded > rate x net paid > "rate not set" with no number, D-32). Expenses = the `expenses` ledger by `business_date`, **voided rows left out** (counted in `voidedExpenseCount`). **Net profit before income tax = gross profit - commission - expenses.** Integer satang; a loss is negative, never clamped.
- **One base, and what "incomplete" means.** An order with an uncosted line keeps its revenue in the P&L but adds no cost; an order with "rate not set" adds no commission. So while `complete` is false, gross and net profit can only be **too high** (every recorded expense is in). `complete` is false if any order was set aside as inconsistent (`excludedOrderIds`), any counted order is uncosted, or any platform order has no commission number. A commission **estimated from a rate is a number** and does not make it incomplete. `incompleteReasons` names which of `orders_excluded | orders_uncosted | commission_rate_not_set`, and `missing` lists the order ids, uncosted menu item ids and platforms. The `margin` block is the unchanged `periodMargin` (costed orders only); its gross profit differs from the P&L gross profit by exactly `uncostedRevenueSatang`.
- **`platform_fees` vs commission: the LARGER is deducted (amendment, owner-approved 2026-10-21; replaces "both are deducted" and the `platformFeesAlsoCommission` flag).** Commission is per-order (recorded or rate based) and is not inside `expensesSatang`; the `platform_fees` expense category is inside `expensesSatang` and `expensesByCategory`. When BOTH are above 0 in the period, only the larger is deducted: `platformFeesBasis` is `commission` or `platform_fees_expenses` (`only_one` when only one side, or neither, has a figure; a recorded commission of 0 is "no figure"; a tie is `commission`), and the smaller is `platformFeesNotDeductedSatang`, added back in the net. Both raw numbers stay in the answer (`commissionSatang`, `platformFeesExpensesSatang`, `expensesSatang` unchanged). The screen names the side used (`pnl.fees.*`).
- **Food cost: the LARGER of cost of goods and `ingredients` is deducted (same amendment).** Cost of goods comes from menu cost snapshots (D-32) and may be the same food as the `ingredients` expense. When both are above 0, only the larger is deducted: `foodCostBasis` is `cost_of_goods` or `ingredients_expenses` (`only_one` otherwise; a tie is `cost_of_goods`), the smaller is `foodCostNotDeductedSatang`, added back. Gross profit stays revenue - cost of goods (raw). Other expense categories are untouched. The rule lives in one pure helper, `@sds/finance` `overlap.ts`, used by the P&L and the tax estimate.
- **Net, with both rules:** `net = gross - commission - expenses + foodCostNotDeducted + platformFeesNotDeducted`.
- **Month rows apply the rules to their own month,** so the months need not add up to the whole-range total (one month's larger side can differ from the whole range's). Chosen as the plain reading of "the larger in the period"; the owner may prefer months that add up exactly (they would then use the range's side everywhere). In `docs/p7-pnl-sample.md` the months add to 361.50 and the range is 368.50.
- **Per month.** When the range touches more than one calendar month the answer has `months`: one row per month that has an order or an expense (empty months are left out), each with the same figures and its own `complete`, computed on that month's rows (the first and last month may be partial). Orders set aside as inconsistent carry no date here, so while any exist every month is marked incomplete.
- **Gov co-pay.** Revenue is the full amount on the sale date (inside revenue); `govCopay.revenueSatang` shows how much of the revenue came that way. The receivable until the next-day settlement is **not tracked** (owner decision 2026-10-21: a settlement mark is not needed, so it is out of P7): no settlement date or "received" mark exists on payments (only a free-text `settlementNote` on the scheme), so the answer says `receivable: 'not_tracked'` rather than presenting the co-pay revenue as unsettled money.
- **Open exit criterion:** "P&L for a sample month agreed by the owner or accountant" (PHASE-07) is still OPEN; the hand-check sheets `docs/p7-pnl-sample.md` and `docs/p7-tax-sample.md` are updated for these rules and wait for the owner.
- **Not decided:** accrual of rent or other costs across months (expenses count on their entered date only); a PDF/CSV of the P&L; income tax from the net profit (next part).

## D-34 · P7 income tax estimate: P&L to taxable income, yearly rules data, 0.5% threshold, half-year allowances — Accepted with amendments (set by Claude on 2026-10-20 from the owner's P7 answers and the Revenue Department (RD) documents read that day; owner approved 2026-10-21 with the larger-of rules below)
- **What it is.** `GET /v1/reports/tax?year&period=annual|half` (owner only, `finance.pnl`, no step-up, `no-store`) and an owner tax profile `GET|PUT /v1/settings/tax-profile?year` (read `finance.pnl`; save `settings.tax_profile`, owner, step-up, audit `settings.tax_profile_update`, whole profile of the year replaced). `year` is the **Buddhist Era** tax year everywhere (2569 = 2026): the rules files, `tax_profiles.year` (it was unused before) and the API. A year with no rules file is **refused** (422 `TAX_RULES_NOT_AVAILABLE`), never answered with another year's numbers. The result is an **estimate, not a filing**: it always carries `ruleYear`, `status: "proposed - confirm with the Revenue Department"`, `disclaimerKey` and `notes` as i18n keys (th, en), and `sources` (the RD URL and the date read, per rule).
- **P&L to taxable income.** Income is section 40(8). **Assessable income = P&L revenue** (net paid of counted orders on `business_date`; gov co-pay counts at its full amount). **Actual expenses = cost of goods + platform commission + unvoided ledger rows, minus the smaller of each overlapping pair (the larger-of rules of D-33)**, i.e. exactly what the P&L deducts: `methods.actual.netBeforeAllowancesSatang` equals the P&L `netProfitSatang` for the same range (a test pins it). **Flat expenses = 60% of revenue** (RD rate table 2, item (9) restaurant, food and drink). Net income = income - expenses; allowances are deducted; tax is on the rest and **never below 0** (a loss pays no tax and the negative figure is still shown). The owner chose actual expenses; the estimate shows both and names the cheaper one but does not switch (`methodPreference` null reads as actual). One method for the whole income, as RD says.
- **Known weaknesses, flagged in every answer.** (1) Cost of goods comes from the owner's menu cost estimates, not receipts (`tax.note.costOfGoodsEstimated`). (2) It can overlap the ledger category `ingredients`, and the commission can overlap `platform_fees`: **only the larger of each pair is deducted (owner decision 2026-10-21)**; the answer carries `foodCostBasis`, `platformFeesBasis` and the not-deducted amounts (replacing `foodCostMayBeCountedTwice`), and one note says which side was used (`tax.note.foodCostCostOfGoodsUsed|foodCostIngredientsUsed|platformFeesCommissionUsed|platformFeesExpensesUsed`; the old `tax.note.foodCostTwice` is gone). The tax estimate previously had no platform-fees note. (3) If the P&L is not `complete`, expenses are understated, so the tax can only be too HIGH (`tax.note.pnlIncomplete`). (4) Actual expenses need records (`tax.note.expensesNeedRecords`). Depreciation, the owner's own pay and personal spending are not modelled.
- **Rules are data.** `packages/finance/src/tax-rules/th-pit-<year>.ts` exports a `TaxRules`; `registry.ts` lists the years. `estimateTax` takes the rules as a parameter and holds no year number (a test runs a synthetic 2570 set through the same code). **A new year is one new file plus one line in the registry; no estimator logic changes** (the exit criterion, with that registry line counted as data). Each rule block lists its RD sources and the date checked.
- **Half-year (ภ.ง.ด.94) vs annual (ภ.ง.ด.90).** Rates are the same (RD FAQ 61549). Allowances differ: the 2569 ภ.ง.ด.94 instruction (Ins94 p.3) states the personal allowance as **30,000 baht** (spouse 30,000, child 15,000, parent 15,000, i.e. half of the annual 60,000 / 60,000 / 30,000 / 30,000 on the ภ.ง.ด.90 instruction p.7), so the rules file holds 30,000 as a stated figure. For allowances the owner enters (stored as annual amounts) the half-year figure is **half, rounded down**: a stated assumption, because RD counts some (home loan interest, life insurance) by what was actually paid Jan-Jun. Entered allowances are not checked against caps or eligibility (`tax.note.allowancesUnchecked`); no cap engine is built. The half-year tax already paid is credited against ภ.ง.ด.90 (RD FAQ Q6.4); no payment is stored, so the annual figure does not subtract it (`tax.note.halfYearCredit`).
- **The 0.5% method (section 48(2)).** RD pages disagree on the threshold: the two **current-year form instructions** (ภ.ง.ด.94 for 2569 p.15 and ภ.ง.ด.90 for 2568 p.6) and rd.go.th/555.html say income of **120,000 baht or more**; two older RD texts (page 31847, updated 2022, and letter กค 0702/9340 of 2009) say **60,000**; our own earlier docs said 1,000,000, which no RD page gives. The Revenue Code text itself was not reachable, so the threshold stays `thresholdStatus: 'conflict'` in the rules file (120,000 used, 60,000 recorded). **It cannot change any answer:** the method is waived when 0.5% of income is **5,000 baht or less** ("ไม่เกิน 5,000", inclusive, both current forms and RD page 31847), which is income of 1,000,000 baht or less; above that both candidate thresholds are already exceeded. So the method is shown **only when it applies** (0.5% over 5,000 baht), with a note that the threshold sources conflict and the result is the same either way; between the lowest and the used threshold (impossible with 2569 numbers, covered by a test) it would be shown as "not applied, threshold unconfirmed". The comparison is on the exact product (no rounding flip at 1,000,000). When it applies, tax = the higher of the normal tax and 0.5% of gross income; when it is waived, the normal tax.
- **Rounding.** Tax is worked in whole satang: the progressive tax is summed over the steps and rounded **once, half up**; the flat expense and the 0.5% tax use the shared `applyBasisPoints` (half up). RD's tables are in whole baht and the pages read give no rounding rule, so the last satang is **unconfirmed**.
- **Watches (data driven, no new tables).** Filing duty (single person: income over 60,000 baht in Jan-Jun for ภ.ง.ด.94, over 60,000 for the year; window 1 Jul - 30 Sep, and 1 Jan - 31 Mar of the next year, the 2568 form's dates assumed for 2569; late: 1.5% a month and a fine up to 2,000 baht; `filing.pastDue`). VAT: registration when sales are **more than** 1,800,000 baht (RD ruling 0702/3397), `below | near (80%, our choice) | over`. e-Payment: 3,000 incoming transfers, or 400 with 2,000,000 baht, per bank per year; the POS counts only its confirmed PromptPay payments of the period, a floor, and the status says `reached` only on that floor. VAT and e-Payment compare the period's income or count (for the half-year that is Jan-Jun only).
- **Not decided / not built.** A tax screen (the answer is ready for one); recording the ภ.ง.ด.94 amount paid; spouse and children allowances as typed fields; whether to put the owner's own annual allowances through a cap table; a PDF or accountant export of the estimate.

## D-35 · P7 receipts and payments report (รายงานรับ-จ่าย, the Revenue Department's รายงานเงินสดรับ-จ่าย) — Accepted 2026-10-21 (proposed by Claude from the owner's P7 kickoff answer 9, "according to recommended standards"; the owner answered the part-6 questions on 2026-10-21 and the amendments below replace the earlier defaults)
- **What the Revenue Department expects (read 2026-10-21).** Individuals with section 40(5)-(8) income who are **not VAT-registered** must keep a daily income and expense account in at least the prescribed form: Director-General announcement on income tax No. 161, 21 Dec 2549 (https://rd.go.th/33300.html, page updated 2022-02-10), whose attachment (https://rd.go.th/fileadmin/images/image_law/images/prob.pdf, read as page images) is the form **รายงานเงินสดรับ-จ่าย**. Columns: date (วัน/เดือน/ปี, B.E.), item (รายการ), receipts (รายรับ), **payments (รายจ่าย) split into buying goods (ซื้อสินค้า) and other expenses (ค่าใช้จ่ายอื่นๆ)**, remark; its example ends with a summary of receipts, payments and their difference. Credit sales and purchases are entered on the day they are paid. Entries within 3 working days, in Thai. **No balance column.** A second source, the Krungsri guide, only repeats this. If the shop becomes VAT-registered the duty changes (tax invoices and VAT accounts); this report does not cover that.
- **It is a working record, not a filing, and not a bank statement.** `GET /v1/reports/cash?from&to[&emptyDays=true]` (owner only, `finance.pnl`, no step-up, `no-store`, range at most 366 days) and the page `#/cash` say so; they do not carry the owner's name or national ID and are not a substitute for the form the owner keeps. The route, file and permission names keep "cash" (stored keys and URLs are not renamed); the words on screen do not.
- **Columns (one row per business day, a total row, and month totals when the range spans months).** Date; receipts per payment method (cash, PromptPay, gov co-pay, platform, other); total receipts; **buying goods**; **other expenses**; total payments; **running net** (ours, not on the form). The summary (receipts, payments, receipts less payments) is the form's. Rows are per day, not per transaction: the ledger and the order list hold the detail. The CSV has the same columns, ISO dates (as in P6, accepted by the owner 2026-10-21), baht with two decimals from integer satang, BOM, formula guard; the on-screen dates are Buddhist Era in Thai.
- **Receipts = all methods (owner answer 2026-10-21: the shop has no cash drawer, 100% of sales are bank transfers into the owner's own account).** Exactly the revenue rule of `03-data-model.md` section 6 (D-30): paid, not cancelled orders on their `business_date`, each confirmed payment minus its own partial refunds, via the same `isCounted` / `keptPayments` helpers. Every method column adds up to the day's revenue, and the answer carries `reconciliation` (the revenue report's total and the difference, always 0); a property test and an API test compare it with `/v1/reports/revenue`. The `cash` method keeps its column (confirmed cash payments minus cash refunds; 0 while there are none) and, if cash payments ever appear, they count as receipts like any other. An order that is not fully paid counts nothing yet, even if some money was taken (same as revenue).
- **Timing.** Co-pay and platform receipts appear on the **sale date**, as revenue does: the RD form is on a cash basis, but gov co-pay arrives at the next-day settlement and platform money at the payout, and neither is tracked (D-33; the co-pay receivable and settlement mark are out of P7, owner decision 2026-10-21). Platform receipts are the platform price, not the payout, and the commission is not a payment unless it was entered as an expense.
- **Payments and "buying goods" (owner answer 2026-10-21).** Unvoided `expenses` by their `business_date` (future dates included, D-31). Buying goods (ซื้อสินค้า) = the expense categories flagged `buyingGoods: true` in the `expense_categories` settings JSON (no migration): the defaults are `ingredients` and `packaging` true and the other seven false; a category the owner adds is ticked by default in the add form, and the Expenses screen's category editor has a checkbox per category (a payment-verification fee, for example, is not goods). The flag is kept when a category is switched off, so old expenses still count; changing it is audited by key (`buyingGoodsChanged` in the `expense.categories_update` row). Every other category is "other expenses". The API passes the flagged keys to `cashReport` as `purchaseCategories`; `DEFAULT_PURCHASE_CATEGORIES` (ingredients, packaging) applies only when a caller gives none.

A later optional field `paid_with` on `expenses` would remove it; not built (needs a migration and a decision).
- **Start amount (was "opening cash"; owner answer 2026-10-21).** The setting keeps its stored key `cash_opening` = `{amountSatang, asOf}` (both null until set; no built-in value, and no running net is ever shown as 0), its routes `GET|PATCH /v1/settings/cash-opening` with `expectedVersion`, its permission `settings.cash_opening` (owner only, step-up, audited `settings.cash_opening_change`, owner alert `settings.cash_opening_changed`), and it stays off the realtime feed and out of `SYNCED_SETTING_KEYS`; the settings read also answers "not set" to any other role. Renaming the key would need a data migration and re-keyed audit/alert names for no gain, so only the words changed: th "ยอดตั้งต้น", en "Start amount". The amount is the owner's starting figure at the **start** of the `asOf` business day (no cash is counted); both are set or cleared together.
- **Running net, not a balance.** The running net at the end of a day = start amount + receipts (all methods) - payments, from `asOf` up to that day; a day has `netSatang` = receipts - payments. Days before `asOf` have `runningNetSatang: null`. When the range starts after `asOf`, the API first works out the net from `asOf` to the day before `from` with the same pure function over windows of at most 366 days, and passes it as `broughtForwardSatang` (no second rule in SQL). Orders set aside as inconsistent in those windows make the answer `complete: false` too. The report gives `runningStartSatang` and `runningEndSatang` (null when the start day is after the start / the end of the range) and `openingNotSet`. The screen and the CSV label it "ยอดสุทธิสะสม / Running net" and say on screen that **it is not a bank statement**: platform payouts and co-pay arrive later and settlement is not tracked. Renamed from `balanceSatang`, `startBalanceSatang`, `closingBalanceSatang` and `cashNetSatang` (the totals keep `receiptsMinusPaymentsSatang`, which is the same figure).
- **Empty days** are left out by default (the running net carries over them); `emptyDays=true` lists them.
- **Export** `GET /v1/reports/export/cash.csv` (`data.export`: owner, step-up, audit `report.export` with kind `cash`, range, row count and set-aside count, no figures), file `cash-<from>-<to>.csv`. The last column is the running net; the total row leaves it empty (a running figure is not a sum). The dev mock does not serve the CSV, as for the P6 files.
- **Not decided / not built.** The `paid_with` field; tracking gov co-pay settlement and platform payouts as money received on the day they arrive (the owner does not need it, 2026-10-21); one row per transaction (the form's own layout) instead of per day; the owner's name and ID on a printable form; a PDF.
