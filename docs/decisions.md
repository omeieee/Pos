## D-01 · TypeScript monorepo — Proposed
- **Decision:** TypeScript (strict) in every app and package. pnpm workspaces + Turborepo. Biome for lint and format.
- **Why:** one language end to end. Zod schemas and types are shared by `api`, `pos-web` and `liff-web`, so a change to an order field breaks the build instead of production. Turborepo caches build/test per package.
- **Alternatives:** Nx (heavier); separate repos (types drift); ESLint + Prettier (two tools instead of one).
- **Revisit if:** a lint rule we need exists only in ESLint.

## D-02 · Backend runtime — Proposed
- **Decision:** Node.js 24 LTS (move to 26 LTS once it enters LTS in Oct 2026), Fastify 5, `fastify-type-provider-zod`, Pino logging, `@fastify/websocket`, `@fastify/rate-limit`, official `@line/bot-sdk`.
- **Why:** the owner already plans Fastify for ntfy. It is fast and schema-first. The same container runs on the Oracle VM, the future Mini PC, or any Docker host, so we are not locked to one provider.
- **Alternatives:** Hono on Cloudflare Workers (no server to maintain, but runtime limits and harder to move on-site); NestJS (more ceremony); Supabase Edge Functions (vendor-specific).
- **Revisit if:** hosting moves to a serverless platform.

## D-03 · Database — Open (Q1)
- **Decision:** PostgreSQL 17 or newer, accessed through Drizzle ORM, with SQL migrations generated by drizzle-kit and committed.
  - **Path A (Oracle Ampere A1 VM):** Postgres runs in Docker on the same VM.
  - **Path B (1 GB E2.1.Micro VM):** managed Postgres. Supabase free tier, used as plain Postgres through its connection string (Neon is the alternative).
- **Why:** orders, items and payments are relational, and reporting needs SQL (`date_trunc`, window functions). Drizzle keeps the SQL visible and typed. Plain Postgres lets us move between Oracle, Supabase and a Mini PC.
- **Alternatives:** Firestore (realtime built in, weak for reports); SQLite/PocketBase (simple, fewer reporting tools); Cloudflare D1 (ties us to Workers).
- **Revisit if:** Q1 is answered (VM shape), or the database grows past the free limits.
- **PGlite version (2026-09-29, P1):** pinned to **0.4.x, which embeds PostgreSQL 17**, the same major as Supabase (17.6). PGlite 0.5.x embeds PostgreSQL 18, where migrations could use PG18-only features that then fail on Supabase. Upgrade PGlite only together with the Supabase major version. Migrations are plain SQL/plpgsql with no extensions, so the same set runs on both.
- **Status note (2026-09-29):** the VM is a **VM.Standard.E2.1.Micro (1 GB RAM) in ap-singapore-1**, so **Path B** applies. Postgres runs on Supabase free, created in the Singapore region next to the VM. Record: [infra/oracle/README.md](../infra/oracle/README.md).

## D-04 · Realtime sync — Accepted (built and deployed 2026-10-02)
- **Decision:** the server is the only source of truth. Every write goes through the API in a DB transaction. Each synced row has a `rev` taken from one global Postgres sequence. After commit the API broadcasts `{type, id, rev, data}` over WebSocket. A reconnecting client calls `GET /v1/sync?since=<rev>` to catch up. Creates carry an idempotency key, and updates carry `expectedVersion` (HTTP 409 on conflict).
- **Why:** it is simple, stays correct after disconnects, and does not depend on Supabase Realtime or Firebase.
- **Alternatives:** Supabase Realtime (lock-in; not available on Path A); CRDT/local-first sync (overkill for one shop).
- **Revisit if:** we run more than one API instance. Then add Postgres `LISTEN/NOTIFY` for fan-out.
- **Status note (2026-10-02, as built):** the WebSocket authenticates with a first message (a browser cannot send headers) and the server re-checks the session on every 25 s beat without extending it, so a listen-only device gets 4401 at its idle limit and the client must keep the session alive or re-sign-in. The feed uses column allow-lists per table and role permission (payments `payment.record`, settings `settings.view`, customers `customer.view`); costs, staff, devices, sessions, audit and expenses never travel and the PromptPay ID is masked. Clients apply a frame only if its `rev` is higher and rewind 200 revs once per catch-up, because a transaction that commits late can carry a lower `rev` than one already sent.

## D-05 · Frontends — Proposed
- **Decision:** React 19 + Vite + TypeScript, TanStack Router and Query, Tailwind CSS v4 + shadcn/ui (Radix), Apache ECharts for charts, i18next, `vite-plugin-pwa`, and Dexie (IndexedDB) for the offline outbox. Two apps:
  - `apps/pos-web`: every staff function (POS, order board, kitchen view, menu, payments, back office, settings), gated by role.
  - `apps/liff-web`: the customer app that opens inside LINE.
- **Why:** one staff app means one login, one realtime connection and one deploy. The customer app stays small for LINE's in-app browser.
- **Alternatives:** SvelteKit (smaller bundles, less familiar); Next.js (server rendering not needed); a separate back-office app (more to deploy).
- **Revisit if:** the back office grows large enough to split into `apps/admin-web`.
- **Status note (2026-10-01, from the QA review of the first staff-app slice):** the auth slice was built with a hash router, plain CSS on the `--sds-*` design tokens, a small custom translator in `packages/i18n` and a custom token store, and none of TanStack Router/Query, Tailwind, shadcn, i18next, `vite-plugin-pwa` or Dexie. That is acceptable for the sign-in screens (smaller bundle, hash URLs also suit Capacitor and Electron `file://` origins). **Four things must be decided before order entry and the offline outbox (P3 tasks 7 and 8):** (1) routing that can express `#/orders/:id` (the current `pathFromHash` matches one segment); (2) how server state is cached and invalidated by realtime events; (3) the IndexedDB layer for the outbox (Dexie or raw IndexedDB behind the platform seam); (4) an app-shell service worker, because an iPad that reloads while offline cannot load the app today, which conflicts with docs/02 section 8.
- **Status note (2026-10-02, the four items decided under the owner's standing authorization):** (1) **Routing:** keep the hash router and extend it to match parameterised paths such as `#/orders/:id`; no TanStack Router. (2) **Server state:** a small custom store keyed by entity id that applies an event only when `event.rev` is greater than the stored `rev` (02 §5), fed by the WebSocket and `GET /v1/sync?since=`; no TanStack Query, because per-entity `rev` ordering and catch-up are the cache rules. (3) **IndexedDB for the outbox:** Dexie, wrapped behind the platform seam (`apps/pos-web/src/platform/`) so features never import it and the native shells can swap the implementation. (4) **App-shell service worker:** `vite-plugin-pwa` (Workbox) precaching the app shell only, with a navigation fallback and no caching of `/v1` responses; registration sits behind the platform seam because service workers do not run on Electron `file://` origins and are often unavailable in Capacitor. Tailwind, shadcn and i18next stay out (plain CSS on the design tokens and the `packages/i18n` translator remain).

## D-06 · Customer channel in LINE — Proposed
- **Decision:** the LINE Official Account "แซ่บโดนเส้น" with the Messaging API for chat and webhooks. The customer ordering app is a **LINE MINI App channel (unverified)** built with the LIFF SDK. Fallback: a LIFF app on a LINE Login channel, which uses the same code. **All channels sit under one LINE provider**, because a customer's `userId` is only the same across channels of the same provider.
- **Why:** since Feb 2025 LINE recommends creating new LIFF apps as MINI Apps and plans to merge LIFF into MINI App. Unverified MINI Apps need no review. LINE's docs say that since 11 Mar 2026 MINI App channels can be created for services in Thailand. Verification is only possible through a certified provider in Thailand, and it is what unlocks free "service messages", so it is not planned.
- **Revisit if:** a certified-provider route becomes available and worth the cost.

## D-07 · Manual payment confirmation — Accepted (owner requirement)
- **Decision:** staff confirm every payment by hand. They count cash, and they check PromptPay or government co-pay money in the bank or ถุงเงิน app. A customer can tap "โอนแล้ว" (I've paid) and attach a slip, but that only moves the payment to *awaiting confirmation*. There is no payment gateway and no paid slip-verification API.
- **Why:** there are no transaction fees and no provider dependency.
- **Revisit if:** volume makes manual checking a bottleneck. The option then is a bank merchant QR with an API; fees apply.

## D-08 · Government co-pay method — Proposed (depends on Q2)
- **Decision:** a generic payment method, "โครงการรัฐร่วมจ่าย", preset for **ไทยช่วยไทย พลัส 60/40**. It has configurable name, government share, daily cap, active dates and hours, and allowed channels. It is **disabled outside those dates and hours**. The customer pays **face-to-face at the storefront** by scanning a QR that staff create **per transaction** in ถุงเงิน. The QR is **never sent through LINE**. LINE customers can pick it as "pay at the storefront".
- **Why:** the scheme rules require per-transaction QRs, scanning at the storefront and GPS (see [04-integrations.md](04-integrations.md#3-government-co-pay-scheme-thai-chuay-thai-plus)). Schemes also change name and ratio every few months.
- **Revisit if:** the scheme's terms allow remote payment.
- **Channels (2026-10-02):** co-pay is refused for `grab` and `lineman` orders (the platform takes the payment) as well as room and platform delivery; a LINE pickup order paid at the counter stays allowed, because that payment is face to face.

## D-09 · LINE messaging budget — Proposed
- **Decision:** anything the customer triggers gets a **reply** (free). After ordering, the customer app calls `liff.sendMessages()` so the order summary and QR go out as a free reply. **Push** messages, which count against the quota, are used only for "order ready" and for messages staff start themselves. A quota tracker holds a policy switch (`always` / `ready-only` / `off`) and warns at 80%. Customer questions are answered by hand in the LINE OA Manager chat, which is free.
- **Why:** the Thailand free plan counts 300 push/multicast/broadcast/narrowcast messages a month. Replies, chat and auto-responses are not counted.
- **Revisit if:** LINE orders pass about 250 a month. Then upgrade to the Basic plan (฿1,280/month for 15,000 messages as of Sept 2026).

## D-10 · Hosting — Open (Q1, Q8)
- **Decision:** the Oracle Cloud VM runs Docker Compose with `api`, `postgres` (Path A only), `backup` and `cloudflared`, plus `ntfy` in P8. **Upgrade the Oracle account to Pay-As-You-Go** with a small budget alert: Always Free resources stay free, and idle instances are no longer reclaimed. Cloudflare provides DNS, TLS, Tunnel (no inbound ports open on the VM), Pages (static frontends) and R2 (backups and images). **The one paid item is a domain name.**
- **Why:** all of it is free, and one VM is simple enough for one owner to run. The Compose stack is portable to a Mini PC or a VPS for disaster recovery.
- **Alternatives:** see [05-infrastructure.md](05-infrastructure.md#2-options-compared).
- **Revisit if:** Q1 shows the VM is a 1 GB Micro (switch to Path B), or Oracle becomes unreliable.
- **Status note (2026-09-29):**
  - The VM is an E2.1.Micro in ap-singapore-1 on a **Free Tier account (not PAYG)**, so it runs Path B: `api`, `backup` and `cloudflared` only, with images built in GitHub Actions and pulled from GHCR, plus a 2 GB swap file.
  - **Idle reclamation risk remains on Free Tier.** Path B mitigates it: the VM is stateless (data in Supabase, backups in R2), so a reclaimed VM is rebuilt from scripts. Upgrading to PAYG is still recommended; the owner decides.
  - The SSH key is kept outside git (see [05 §6](05-infrastructure.md#6-oracle-vm-setup-and-hardening-checklist-p2)).
- **Accepted 2026-09-29 (interim, no domain):**
  - The API is reached through **Caddy on the VM with a Let's Encrypt certificate on a free hostname** (sslip.io name from the VM IP, e.g. `138-2-67-89.sslip.io`; DuckDNS as fallback).
  - The VM opens **only 80/443** (plus SSH restricted to the owner). Caddy replaces `cloudflared`.
  - `pos-web` and `liff-web` are on Cloudflare Pages (`*.pages.dev`).
  - **Target once a domain is bought:** named Cloudflare Tunnel and no open ports, as designed. Switching means updating the LINE webhook and app URLs once.

## D-11 · Money and time — Proposed
- **Decision:** amounts are stored as integer **satang** (`bigint`), in THB only. The server always computes totals. Timestamps are stored as `timestamptz` in UTC and shown in Asia/Bangkok time. Reports group by `business_date`, whose cutoff is configurable (default 04:00, so late-night sales count for the previous day).
- **Why:** no floating-point rounding errors, and daily totals are correct even if the shop closes after midnight.
- **TypeScript representation (2026-09-29, P1):** in code, satang is a branded `number` that must be a safe integer (`Number.isSafeInteger`, ±9×10¹⁵ satang), not JS `BigInt`. The DB column stays `bigint`, read by Drizzle in `number` mode. Why: `BigInt` cannot go through `JSON.stringify`, Zod-over-HTTP or React without custom serialization, and the shop's amounts are many orders of magnitude below the limit. Guards in `packages/shared/money` reject non-integers and unsafe values.

## D-15 · Kitchen printing — Proposed (P8)
- **Decision:** `apps/print-agent` runs on the Mini PC. It keeps an outbound WebSocket to the API, receives print jobs, and prints to the Xprinter XP-80T over the LAN (raw TCP port 9100). Thai text is rendered as a **raster image**, because text-mode code pages break Thai vowels and tone marks. The cloud remains the source of truth, and the Mini PC is only an edge agent.
- **Open (P9):** whether the Mini PC should also run a local copy of the POS for resilience.
- **Note (P10):** the native apps (D-19) could print straight to the XP-80T over the LAN (TCP 9100) — Capacitor has community TCP/ESC-POS plugins for iOS, and Electron can use `packages/escpos` directly. That would make the Mini PC optional for printing. P8 stays as planned, because Safari can't print this way.

## D-16 · Background jobs — Proposed
- **Decision:** pg-boss, a Postgres-backed queue and cron, runs inside the API process. Jobs include overdue-payment reminders, the daily summary, quota checks, retention cleanup and print-job retries.
- **Why:** no extra service such as Redis to run.
- **Revisit if:** jobs slow down API responses. Then split them into an `apps/worker` process running the same code.

## D-17 · Staff authentication — Proposed
- **Decision:** the owner registers each device once, which issues a long-lived device token that can be revoked. Staff unlock with a personal 4–6 digit PIN (hashed, rate-limited, locked after repeated failures). Roles are owner, manager, cashier and kitchen. The owner's back-office login uses a password plus TOTP. Sensitive actions (**changing the PromptPay ID**, managing staff, voiding a paid order, exporting data) ask for the password again.
- **Proposed amendments from the first build slice (2026-10-01, status stays Proposed; some items are in review):**
  - **Tokens and sessions:** opaque 256-bit random bearer tokens stored only as SHA-256; sessions are database rows, so a revoke or a role change takes effect at once. PIN sessions last 12 h (idle 2 h), owner sessions 8 h (idle 30 min), and PIN sessions are bound to the registered device.
  - **Step-up follows the role, not how the session was opened:** the owner gives password plus a TOTP or recovery code, even on a device unlocked with a PIN; other roles re-enter their PIN. Signing in does not count as step-up. A step-up lasts 5 minutes.
  - **Secrets at rest:** passwords and PINs use scrypt (PINs also peppered with a key derived from `AUTH_SECRET_KEY`); the TOTP secret is AES-256-GCM encrypted under that key; recovery codes are single-use. TOTP is RFC 6238 with a plus/minus one step window and replay protection.
  - **Locks:** 5 wrong PINs lock for 5 minutes, escalating to 1 hour and 24 hours on repeated lock cycles; PINs for the owner and managers are 6 digits; the owner account locks for 15 minutes after 5 wrong tries, with separate counters for public sign-in and step-up so a stranger cannot keep the owner out of sensitive actions.
  - **Master key:** `AUTH_SECRET_KEY` lives only in the VM `.env` plus an offline copy; the API refuses to start without it; it must never be regenerated on a rebuild or rotated to sign devices out.

## D-18 · Backups and monitoring — Proposed
- **Decision:**
  - Hourly `pg_dump` during opening hours plus a nightly full dump. Dumps are encrypted with `age` and stored in OCI Object Storage (see the status note: R2 dropped). A healthchecks.io ping fires if a backup is missed.
  - An external uptime check on `/healthz`, and Sentry's free tier for errors.
  - A restore drill every month.
- **Targets:** at most 1 hour of data lost (RPO), and back online within 2 hours (RTO).
- **Status note (2026-09-29, P2 kickoff):** the owner chose **OCI Object Storage only** for backups (no card at Cloudflare, so no R2). Risk accepted: the VM and the backups are with one provider. Mitigation to consider: a weekly automatic copy to the owner's laptop. The age private key is kept printed plus on a USB drive (no password manager yet).

## D-19 · Client platforms and the native path — Proposed (depends on Q13)
- **Now (P3–P5), web first:**
  - Staff use `pos-web` in **Safari on iPad and iPhone** and in standard desktop browsers (Chrome, Edge, Firefox, Safari on macOS).
  - Staff devices should use **Add to Home Screen**. It is still Safari, but runs full screen, can receive Web Push (iOS 16.4+), and is exempt from Safari's rule that deletes a site's stored data after 7 days without use.
  - A plain Safari tab also works, with those limits (see [02 §12](02-architecture.md#12-client-platforms-and-the-native-path)).
- **Later (P10), native installable apps built from the same React code:**
  - **iPad and iPhone: Capacitor** (`apps/pos-mobile`). It has an official push-notification plugin, keep-awake and secure storage, and community TCP/ESC-POS plugins for printing to the LAN printer from iOS.
  - **Windows, macOS and Linux: Electron** (`apps/pos-desktop`). Its Node main process can reuse `packages/escpos` (TypeScript) to print directly over LAN or USB. It uses the same Chromium engine on all three systems, so Thai text renders the same everywhere.
- **Built now so the native step stays cheap:**
  - the API base URL is set by config (no same-origin assumption);
  - login uses bearer tokens, not cookies (already D-17);
  - the CORS allow-list is configurable, so native app origins can be added later;
  - a thin platform interface in `pos-web` (sound/notifications, wake lock, token storage, print) has **web implementations only**.

  No other native work happens before P10.
- **Why:** one UI codebase for five platforms, with the web version live from day one.
- **Costs and blockers, for the owner to decide (Q13):**
  - iOS distribution (TestFlight, Ad Hoc, Unlisted or App Store) and macOS notarization require the **Apple Developer Program, US$99 a year**.
  - iOS and macOS builds need **macOS + Xcode**, and the owner currently works on Windows.
  - Windows (Microsoft Store registration is free) and Linux cost nothing, so **desktop can come first**.
- **Alternatives:** Tauri 2 for desktop and/or mobile (much smaller installers, but printing needs Rust or a sidecar, and iOS push relies on community plugins); React Native or Flutter (UI rewrite); staying PWA-only (free, but no LAN printing or reliable alarms on iOS).
- **Status note (2026-09-29):** deferred. Native apps are a future project. The owner plans to buy a MacBook for Xcode/iOS work, and nothing native is built until then. The P1/P3 seams listed above are still built, because they cost almost nothing.
- **Revisit if:** at P10 the desktop app will *not* print directly (printing stays with the print agent) and installer size or RAM matters on the target PCs. Then choose **Tauri 2** for desktop instead of Electron.
